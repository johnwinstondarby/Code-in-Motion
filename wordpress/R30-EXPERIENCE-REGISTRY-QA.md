# R30 WordPress Experience Registry QA

## Scope

R30 establishes the deployment registry that connects shipped Runtime Experience JSON to the production WordPress Host without adding a second Runtime ingestion contract.

R30 begins from protected `main` at:

`26f094a5da23a66d4b6e94990a15bb30e62710f6`

R30 asks one question:

> Can WordPress derive both browser Experience resolution and release Experience staging from one deterministic data-only registry, while preserving existing Runtime validation and protected-release discipline?

## Why R30 follows R29

R29 established:

`human-authored .cim → compiler → validated localis.cim/v1`

The WordPress browser path already establishes:

`Experience JSON → fetch → ingestExperience() → Host → Runtime`

The missing deployment seam is the authoritative mapping between an Experience identity and its shipped JSON asset.

Before R30, that mapping is duplicated:

- `wordpress/assets/bootstrap-module.mjs` owns a handwritten Experience-path map;
- `tools/build-wordpress-release.mjs` owns a separate handwritten Experience staging list.

R30 replaces those duplicate deployment facts with one canonical registry.

## Definition artifacts

## R30 deliverables

### 1. Canonical deployment registry

Create:

`wordpress/experiences/registry.json`

with the exact ADR 0038 schema.

The registry is deployment data only.

### 2. Registry validator/check surface

Add deterministic tooling that validates:

- exact schema and key sets;
- canonical record ordering;
- canonical Experience IDs;
- unique IDs;
- canonical JSON asset names;
- referenced asset existence;
- Runtime JSON parseability;
- successful production `ingestExperience()`;
- registry-ID / Runtime-ID equality;
- deployment-copy freshness;
- browser registry projection freshness;
- release-staging correspondence.

Expose the check through `package.json` and include it in `npm run verify`.

### 3. WordPress deployment directory

All registered deployable Experience JSON must exist beneath:

`wordpress/experiences/`

The existing synthetic Experience remains there.

The R27 Git Runtime Experience gains a deterministic WordPress deployment projection in that directory while retaining its existing canonical generated source/output ownership.

### 4. Browser registry projection

Replace the handwritten browser Experience-path table in `wordpress/assets/bootstrap-module.mjs`.

Generate `wordpress/assets/experience-registry.generated.mjs` from the canonical registry. The generated projection must contain inert ID/asset data only, carry no path policy, ship inside the version-bearing module graph, and remain freshness-gated against `registry.json`.

The existing `createWordPressExperienceLoader()` API remains unchanged.

### 5. Registry-driven release staging

Remove the independent handwritten Experience source list from the WordPress release builder.

Registered Experience staging must derive from the canonical registry.

### 6. Renderer compatibility proof

Every shipped registered Experience must declare a renderer that resolves through the currently shipped WordPress renderer registry.

This is a verification relationship only. R30 does not merge the Experience and renderer registry contracts.

### 7. Plugin version 0.1.2

R30 intentionally changes the release artifact.

Update all version-bearing release metadata consistently from 0.1.1 to 0.1.2, including:

- `package.json`;
- `package-lock.json`;
- root plugin header;
- WordPress implementation version constant;
- `readme.txt` stable tag/changelog;
- version-bearing release paths generated by the release builder.

The accepted R30 artifact receives a new deterministic identity.

## R30 acceptance gates

R30 closes only when all of the following are proven:

1. ADR 0038 is accepted and matches implementation.
2. The canonical registry has the exact documented schema and key sets.
3. Registry records are in canonical ID order.
4. Duplicate or malformed Experience IDs fail closed.
5. Invalid asset names, traversal attempts, URLs, queries, fragments, slashes, and backslashes fail closed.
6. Every registered asset exists beneath `wordpress/experiences/`.
7. Every registered asset parses as JSON and passes production `ingestExperience()`.
8. Every registry ID equals the validated Runtime Experience ID.
9. The R27 Git WordPress deployment copy is freshness-gated against its canonical generated Runtime JSON.
10. Browser Experience-path resolution derives from the canonical registry, no handwritten Experience-path table remains, and a repository scan proves the two retired deployment-list identifiers are absent.
11. The existing WordPress Experience loader contract remains unchanged and all loader/cache/identity tests remain green.
12. Release Experience staging derives from the canonical registry and no second handwritten Experience staging list remains.
13. Every staged registered Experience corresponds one-to-one with a registry entry.
14. Every shipped registered Experience resolves through the shipped renderer registry.
15. Plugin/release metadata is internally consistent at version 0.1.2.
16. The 0.1.2 release ZIP is deterministic and reproducible under the pinned release Node version.
17. Fresh install from the 0.1.2 ZIP passes the existing authoritative WordPress artifact path.
18. Upgrade testing uses the real prior release tree discovered from first-parent version history and proves 0.1.1 to 0.1.2 warm-cache replacement.
19. Node 20 verification passes.
20. Node 22 verification passes.
21. `CiM / Verify` passes on the final frozen R30 head.
22. `CiM / Floor QA` passes on the final frozen R30 head.
23. `CiM / Browser E2E` passes on the final frozen R30 head.
24. `CiM / Playground` passes on the final frozen R30 head.
25. Final 0.1.2 file count, staged-byte count, module/import counts, ZIP SHA-256, and release-manifest SHA-256 are recorded.
26. PR integration uses a true merge commit into protected `main`.
27. The frozen R30 head is confirmed reachable from `main`.
28. Final closure evidence is recorded on the R30 PR.

## Stop conditions

R30 stops for review if implementation:

- changes Runtime Experience semantics;
- lets Runtime read the WordPress registry;
- adds a second Experience validator;
- adds executable registry fields;
- permits remote or traversal-based Experience asset selection;
- changes the shortcode grammar;
- introduces WordPress-side `.cim` parsing;
- merges Experience and renderer registry authority;
- changes existing Host command/disposal/deep-link ownership;
- alters the WordPress support floor;
- produces unexplained release-tree movement.

## Boundary

R30 establishes:

`validated Experience asset → deployment registry → WordPress loader/release packaging`

R30 does not establish:

`WordPress editor/upload → .cim compiler`

That administration seam remains available for a later checkpoint after the deployment registry is stable.
